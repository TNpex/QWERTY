# SaleTennis BI Analytics

BI-дашборд для анализа наличия товаров и размеров по магазинам сети SaleTennis
(теннис и падел).

**Данные встроены в сайт** (`public/data/`: каталог ~2200 артикулов в 12 категориях,
остатки по размерам в 10 магазинах, история снимков, журнал изменений парсера и
фотографии товаров) — дашборд открывается сразу с реальной картиной остатков.
Можно загрузить и свой XLSX/CSV-файл.

Вкладки: **обзор** (дроби «14 из 100» и разрез по магазинам), инвентарь с
карточками товаров (фото + размерная сетка), **продажи и распроданные товары**,
перемещения между магазинами (список ⇄ карточки с фото), дозакупка с выгрузкой
заявки в XLSX, **🏬 магазины** (профили точек и запреты товаров), графики.

**Каждая вкладка — отдельная страница со своим адресом** (`/inventory`,
`/transfers`, `/stores`, …), поэтому работают кнопки «Назад»/«Вперёд» браузера,
раздел можно открыть по ссылке или закладке, а перезагрузка оставляет вас там же.
Карточка товара тоже имеет адрес — «Назад» закрывает её и возвращает в список.

Все расчёты — **в браузере** (файлы никуда не отправляются); загруженный вручную
файл сохраняется в IndexedDB и переживает перезагрузку страницы.

## 🔎 Глобальные фильтры (все вкладки)

Панель фильтров над контентом любой вкладки:

- **Категория** — Одежда, Обувь, Ракетки для тенниса, Падел-ракетки, Струны, Мячи,
  Аксессуары, Сумки и чехлы, Оборудование и т.д.;
- **Пол** — Все / Женская / Мужская / Детская / Унисекс (определяется по названию:
  «женск…», «мужск…», «для девочек/мальчиков», «детск…/юниор»);
- **Бренд** — Nike, Head, Babolat, 7/6, Solinco, …
- **Тип одежды / аксессуаров** — определяется по названию для категорий «Одежда»,
  «Аксессуары» и «Падел - Аксессуары». Группы подобраны по фактическому каталогу:
  Носки · Футболки и поло · Майки и топы · Шорты · Юбки и платья · Брюки, капри,
  леггинсы · **Верхняя одежда** (куртки, ветровки, жилеты, **лонгсливы**) · Худи и
  свитшоты · Рубашки и блузы · Комплекты (включая спортивные костюмы) · Головные
  уборы · **Грипы и овергрипы** · **Виброгасители** · **Аксессуары для ракеток**
  (утяжелители, трафареты, заглушки, натяжка, маркеры) · **Защитные ленты и
  протекторы** · **Напульсники** · **Суппорты и бандажи** · **Бутылки для воды** ·
  **Сувениры и подарки** (магниты, брелоки, кружки, аромасаше, серьги) · **Книги** ·
  Прочее. Раньше 405 позиций сваливались в «Прочее» — теперь их **2**
  (правила: `SUBTYPE_RULES` в `src/utils/productMeta.ts`, покрыты тестами);
- **Вид спорта** — 🎾 Теннис / 🏓 Падел / 🎽 Теннис-Падел. Ориентация определяется
  автоматически и правится вручную в карточке товара (выбор запоминается):
  - «Падел» — если падел есть в категории или названии («Кроссовки Joma Spin Padel»);
  - **«Теннис/Падел» — одежда, обувь и носки**: они универсальны, в них играют оба
    вида спорта. Слово «Tennis» в названии одежды («Nike Court Advantage Tennis
    Pants») ориентацию не меняет — вещь всё равно продаётся в падел-точке.
    Так было не всегда: раньше одежда и обувь считались теннисными, и магазин с
    профилем «только падел» терял 830 позиций ассортимента;
  - «Теннис» — инвентарь: струны, ракетки, мячи, вибрагасители с явным «теннис»;
  - «Прочее» — сквош, оборудование, сувениры.
  Ручная правка в карточке товара важнее автоопределения: если конкретную вещь
  нужно отдать только теннисистам, поставьте «🎾 Теннис» — и падел-точка её
  больше не получит.

### Карточки товаров и ручные настройки (вкладка «Инвентарь»)

- Переключатель **таблица ⇄ карточки** (маленькие карточки с фото; выбор запоминается).
- Фильтр наличия **Все / В наличии / Отсутствует в магазине / Распроданные**.
  Статусы различаются честно (`src/utils/availability.ts`):
  - **🔴 Распродано** — нет ни одной штуки **нигде** (ни в магазинах, ни на складе);
  - **🟠 Отсутствует** — нет в выбранном магазине, **но есть на других точках**
    (в подсказке видно, сколько штук в сети); появляется только при выбранном
    магазине — раньше такие товары ошибочно помечались «Распродано»;
  - товары, **убранные с сайта**, не теряются: берутся из истории снимков и
    показываются распроданными (бейдж «Убран с сайта», дата и последний остаток).
- **Магазин в «Инвентаре» — та же общая область**, что в «Обзоре» (адрес
  `/inventory?scope=…`): выбрали точку в сайдбаре или в «Обзоре» → инвентарь
  открыт на ней, переключение на «🌐 Все магазины (вся сеть)» возвращает всю сеть.
- Клик по товару — карточка: наличие по магазинам, размерная сетка и ручные
  настройки: **ориентация (Теннис / Падел / Теннис-Падел)**, **«Требуется /
  Не требуется»** для перемещений (услуги — «Не требуется»), **«Поставляется /
  Не поставляется»** (в «Дозакупке» видны только поставляемые) и **«🔥 Сделать
  ходовым»** (огонёк во всех списках + приоритет в «Перемещениях»).
- **Профиль «Мой магазин»** в сайдбаре: «Перемещения» показывают только ваш
  магазин (входящие / исходящие / вся сеть), «Инвентарь» открывается на нём,
  «📊 Обзор» переключается на его область. Профиль хранится только на устройстве
  магазина.
- В карточке товара — блок **«🏬 Правила по магазинам»**: минимум и 🚫 запрет
  для «Моего магазина», любого другого или сразу всех магазинов + статус правила
  в строке каждого магазина (см. ниже).
- Все ручные настройки сохраняются в браузере **автоматически** (скачивать
  ничего не нужно) и переживают парсинги. В сайдбаре — **«Настройки товаров:
  N — скачать JSON»** и **«Загрузить настройки товаров»** для переноса между
  устройствами; если админ положит файл в `public/data/product-settings.json`
  (через «скачать JSON» → коммит), настройки станут общими для всего сайта.
- На вкладке «Продажи» у распроданных позиций виден **последний размер,
  который был на сайте** (по снимкам размеров), с датой.

### 🛒 Корзина saletennis.com из «Перемещений»

Отметьте чекбоксами нужные позиции (товар + размер), **вручную укажите
количество** (−/+ или ввод числа) → **«Перейти к заказу»** → **«Открыть корзину
со списком»** → на открытой странице нажмите кнопку-закладку.

**⚠️ Как устроена корзина saletennis.com (проверено на живом сайте):** корзина
привязана к **сессии браузера** (cookie `PHPSESSID`), а не к аккаунту: даже гость
(в шапке «Войти») видит свою корзину с товарами и может оформить заказ. Поэтому
товары можно добавить только **из вашей сессии браузера**.
Ранний способ «логин/пароль через сервер» наполнял корзину *серверной* сессии,
которую браузер не видит (сообщение «Добавлено», а корзина пустая) — **удалён**.

**Кнопка-закладка (основной способ — без паролей и cookie):**
1. Один раз: «Перейти к заказу» (или «📖 Как заказать») → перетащите тёмную
   кнопку **«🛒 SaleTennis Заказ»** на панель закладок браузера (Ctrl+Shift+B,
   если панели не видно);
2. Дальше: отметили позиции → «Перейти к заказу» → «Открыть корзину со
   списком» → на открытой странице нажали закладку → плашка «Добавляю 1 из N…»,
   товары легли в корзину **вашего браузера**, корзина обновилась сама;
3. Вход на сайт не обязателен: гостевая корзина тоже «ваша» — войдёте и
   оформите заказ позже. Список заказа хранится в памяти страницы (переживёт
   случайное закрытие вкладки; при пустой корзине во входе — один авто-повтор).

**«⚡ Авто-добавление» по сохранённой cookie (альтернатива, без нажатия
закладки):**
1. На вкладке saletennis.com **в том же браузере**: расширение Cookie-Editor →
   Export → скопируйте значение `PHPSESSID`;
2. «🔑 Корзина saletennis» → вставьте → «Сохранить»;
3. Отметьте позиции → «⚡ Авто-добавление» в плавающей панели — товары
   добавятся пакетами, корзина откроется сама.
Cookie хранится только в браузере устройства. Обновляйте её после закрытия
браузера или если сайт выдал новую сессию — иначе API честно ответит «сайт
выдал новую сессию — обновите cookie» и ничего не добавит вслепую.
(В локальной сборке `npm run dev` серверной функции нет — «⚡» недоступно;
закладка и копирование работают всегда.)

Общее для закладки и «⚡»:
- идентификаторы товаров и размеров берутся из `public/data/cart-map.json`
  (собирает парсер при каждом прогоне); одинаковые товар+размер сливаются
  в одну позицию с суммарным количеством;
- позиции без данных карты можно **«Скопировать списком»**;
- серверная функция `api/saletennis-cart.ts` (Vercel) не хранит cookie и не
  передаёт их куда-либо ещё.

#### Количество в заказе (почему раньше было «кол-во: 1»)

**Причина найдена:** окно заказа хранило *снимок* списка (готовую ссылку и числа),
а плавающая панель корзины лежит **поверх** окна — правка количества в ссылку для
закладки уже не попадала, и на сайт уезжало 1 шт.

**Как теперь:**
- счётчик **−/+** есть в трёх местах и значение **общее**: прямо в строке
  рекомендации (появляется при отметке), в плавающей панели корзины и в окне заказа;
- окно заказа считается из выбранных позиций **вживую**: показывает весь список с
  количествами, их можно править и удалять на месте, а «Открыть корзину со списком»,
  «⚡ Авто-добавление» и «Скопировать список» всегда берут свежие числа
  (ссылка `#stcart=…` пересобирается в момент клика);
- плавающая панель **скрывается**, пока открыто окно заказа (больше не перекрывает его);
- логика вынесена в чистый модуль `src/utils/orderSelection.ts` — на него написаны
  регрессионные тесты: 4 шт. доезжают до hash-ссылки и до текста списка,
  1 + 3 в два магазина сливаются в 4, правка количества после «снимка» меняет ссылку.

### 🏬 Профили магазинов (вкладка «Магазины»)

Слева — список точек с бейджами и подписью **«ассортимент: N из M артикулов»**,
справа — профиль выбранного магазина:

| Раздел профиля | Что делает |
|---|---|
| **Вид спорта** | Например, «🏓 Только падел» → теннисные товары не попадают в перемещения этой точки и в её норматив дозакупки. Универсальные товары («Теннис/Падел», прочее) подходят любой точке. ⚠️ Не путайте два пункта: **«🌐 Теннис и падел»** = точка торгует всем (обычный выбор для розницы), а **«🎽 Теннис/Падел»** = точка торгует *только универсальными* товарами (одежда, обувь, носки, прочее) — теннисные струны/ракетки/мячи и падел-специфика в её ассортимент не попадут |
| **Категории** | Можно скрыть отдельные (Струны, Оборудование…) — их товары не предлагаются магазину |
| **Перемещения** | 📴 Выключить совсем (точка не участвует ни как получатель, ни как донор) + **минимум на позицию по умолчанию** |
| **Индивидуальные запреты товаров** | Поиск по названию/артикулу/бренду → «🚫 Запретить»; список запретов с кнопкой снятия |
| **Заметка о магазине** | Свободный текст (виден в профиле) |

**Куда влияет профиль:** «🔄 Перемещения» (получатели и доноры), норматив ходовых
товаров в «🛒 Дозакупке» (минимум в каждом магазине считается только по «своим»
точкам) и «📊 Обзор» по магазину (позиции вне ассортимента точки не попадают в её
знаменатель — их количество показано отдельно).

**Как админу сделать настройки общими для всех устройств.** Скачивание JSON само
по себе ничего не меняет у других — файл нужно положить в репозиторий:

```bash
# 1. на сайте: сайдбар → «Настройки товаров: N — скачать JSON»  (ВСЕ настройки)
#    либо «🏬 Магазины» → «Профиль магазина (JSON)»               (одна точка)
# 2. влить скачанное в общий файл (ничего не затирая):
npm run merge-settings -- ~/Downloads/product-settings.json
npm run merge-settings -- ~/Downloads/product-settings-уфа.json --dry   # посмотреть, не записывая
# 3. опубликовать:
git add public/data/product-settings.json
git commit -m "data: общие настройки товаров и профили магазинов"
git push
```

После деплоя **все устройства подхватят настройки автоматически** при открытии
сайта (импортировать вручную ничего не нужно). Локальные правки устройства имеют
приоритет над общими — если сотрудник наэкспериментировал у себя, в сайдбаре есть
кнопка **«↺ Сбросить локальные настройки»** (вернёт устройство к общим).

⚠️ Не кладите файл профиля одного магазина **вместо** общего — затрутся профили
остальных точек и настройки товаров. Используйте `npm run merge-settings`: он
сливает по тем же правилам, что и приложение при импорте (проверено тестом
`mergeSettingsScript.test.ts`).

**Кнопка «Профиль магазина (JSON)»** выгружает профиль отдельным файлом формата,
**совместимого с общим `product-settings.json`** (`product-settings-<магазин>.json`):
внутри только данные этой точки — её профиль и её индивидуальные минимумы товаров.
Файл можно импортировать обратно (сайдбар → «Загрузить настройки товаров») или
положить в `public/data/product-settings.json`, чтобы профиль стал общим для сайта.
Это заготовка под **личные кабинеты магазинов**: точка правит свой файл (или свой
раздел общего файла) сама. При импорте магазин, описанный в файле, заменяет свой
профиль целиком — снятый магазином запрет не «воскресает» при следующем импорте.

### ⭐🚫 Правила «товар × магазин» (карточка товара)

В карточке товара вместо блока «Мой магазин» — **«🏬 Правила по магазинам»**:

- **«Минимум, шт.»** — для «Моего магазина» или для **любого** магазина
  (в селекторе есть и «🌐 Все магазины»);
- **«Запретить»** — товар больше не предлагается этому магазину в перемещениях
  (на Парина рекомендация остаётся, на Елизаветинском шоссе — исчезает).
  **Запрет сильнее всех остальных правил** и снимается одной кнопкой;
- в строке **каждого** магазина виден статус:
  `✅ перемещение разрешено` · `⭐ минимум N шт.` · `🚫 запрещено` ·
  `⛔ магазин не продаёт «Теннис»` (или категория скрыта / перемещения выключены).

Индивидуальный минимум товара **перекрывает** минимум магазина по умолчанию.
Во «Перемещениях» нехватка до минимума получает бейдж **⭐ Минимум N (есть X)**,
поднимается в начало списка, а получатель заполняется **до минимума** (а не до 2 шт.) —
в получатели попадает и магазин, где остаток уже 2 шт., если минимум больше.

### 🔄 Перемещения: список ⇄ карточки

Переключатель в панели фильтров (выбор **запоминается**): в карточках крупное фото
товара, 🔥, количество дефицитов, остатки по магазинам, размеры «куда» и отметка
**«✓ N поз. · M шт. уже в заказе»**. Кнопка «В заказ: все дефициты» отмечает сразу
все дефициты товара; количество правится в строках списка, в панели корзины и в
окне заказа.

Если профили магазинов что-то отсекают, над списком появляется **плашка**: какие
профили учтены, сколько товаров и по какой правиле скрыто (⛔ вид спорта,
⛔ категории, 🚫 запреты, 📴 перемещения, ⭐ минимум).

### 📊 Обзор: дроби и разрез по магазинам

- **Область**: «🌐 Вся сеть» или конкретный магазин (подставляется из «Моего
  магазина» в сайдбаре) — всё пересчитывается. Область **общая с «Инвентарём»**
  и видна в адресе (`/?scope=Уфа`); при возврате к «🌐 Вся сеть» числа
  пересчитываются обратно сетевые;
- **дроби вместо процентов**: «14 из 100» + полоса доли, процент — мелкая подпись;
- блок **«Как считаются эти цифры»**: позиция = товар × размер × магазин, который
  товар возит; «—» (не возит) в знаменатель не попадает; распроданный артикул —
  нет ни одной штуки; источник — снимок от даты;
- **карточки** (клик ведёт на нужную вкладку): позиции без наличия, распроданные
  артикулы, товары в наличии, остаток шт., стоимость, «везти в магазин» /
  «отдать из магазина», дозакупка, переизбыток;
- **«86 / 100 позиций с наличием»** по каждому магазину (клик открывает его обзор),
  стековая диаграмма «с наличием / без наличия» по категориям и таблица сравнения
  магазинов с итоговой строкой;
- для магазина — блок **«Чем заполнить магазин»** (ближайшие дефициты: что, в каких
  размерах и откуда везти).

Фильтры влияют на KPI, графики, инвентарь, перемещения, дозакупку (включая сумму
заявки и XLSX-выгрузку) и продажи. На «Перемещениях» дополнительно есть фильтр
подтипов одежды: Носки, Футболки и поло, Шорты, Юбки и платья, Брюки/капри/леггинсы,
Куртки, Худи, Головные уборы и т.п.

## 🔗 Страницы и ссылки (роутинг)

Сайт — одно приложение, но каждая вкладка имеет **свой адрес**: работает кнопка
«Назад», раздел можно дать коллеге ссылкой, а перезагрузка страницы не сбрасывает
вас в начало.

| Адрес | Раздел |
|---|---|
| `/` | 📊 Обзор |
| `/inventory` | 🎾 Инвентарь |
| `/sales` | 🔥 Продажи |
| `/transfers` | 🔄 Перемещения |
| `/restock` | 🛒 Дозакупка |
| `/stores` | 🏬 Магазины |
| `/analytics` | 📈 Аналитика |

Дополнительно в адресе:
- **`?product=<id>`** — карточка товара поверх раздела. Открытие добавляет запись
  в историю, закрытие её заменяет, поэтому «Назад» в браузере **закрывает карточку
  и возвращает в список**. Работает на всех вкладках (Инвентарь, Перемещения,
  Дозакупка, Продажи, Магазины);
- **`?scope=<магазин>`** — область «какой магазин смотрим», **общая для всех
  вкладок**: `/?scope=Уфа` открывает обзор Уфы, `/inventory?scope=Уфа` — её
  инвентарь. Выбрали точку в «Обзоре» → перешли в «Инвентарь» → он открыт на ней
  же (и наоборот). По умолчанию подставляется «Мой магазин» из сайдбара;
  «🌐 Вся сеть» — адрес без параметра.

Заголовок вкладки браузера показывает текущий раздел. Роутер свой, без зависимостей
(`src/utils/router.ts`, History API + `popstate`); если `pushState` недоступен,
приложение продолжает работать без смены адреса.

### Что нужно от хостинга

«Чистые» адреса требуют, чтобы хостинг отдавал `index.html` на любой путь:

- **Vercel** — уже настроено: `vercel.json` → `rewrites` (пути `/api/*`, `/data/*`
  и `/assets/*` не переписываются, данные и фото отдаются как раньше);
- **nginx** — `location / { try_files $uri $uri/ /index.html; }`
  (`try_files` сначала проверяет файл, поэтому `/data/products.csv` работает);
- **Apache / .htaccess** (например, Beget):

```apache
RewriteEngine On
RewriteBase /
RewriteCond %{REQUEST_URI} !^/(data|assets|api)/
RewriteCond %{REQUEST_FILENAME} !-f
RewriteCond %{REQUEST_FILENAME} !-d
RewriteRule . /index.html [L]
```

Локально ничего настраивать не нужно: `npm run dev` и `npm run preview` отдают
`index.html` на любой путь сами.

Данные (каталог ~1,2 МБ + остатки ~3 МБ + фото) отдаёт хостинг при каждом

### Фотографии товаров

Основной источник — папка `Product_images` вашего парсера (имена совпадают с
колонкой «Фото»): `npm run images -- <папка>` → `npm run compress-images`
(PNG → WebP 700px, −95%+ объёма) → коммит. Сайт пробует фото по каскаду:
**локальный WebP → локальный PNG → фото с saletennis.com → заглушка**.

**В git хранятся только WebP.** Оригиналы PNG/JPG внесены в `.gitignore`:
один оригинал — это ~0,5 МБ, и за прогон парсинга 24.09.2026 в репозиторий
уехало 2035 PNG ≈ **1 ГБ** (дерево выросло со 136 МБ до 1151 МБ, клон
перестал проходить по обычному каналу). Причина была в связке двух скриптов:
`compress-images.mjs` удалял оригинал только после успешного сжатия, а если
WebP уже существовал — пропускал файл вместе с оригиналом; парсер же на
следующем прогоне не находил свой кэш `<hash>.png` и скачивал всё заново.
Исправлено в трёх местах: `compress-images.mjs` удаляет оригинал и при
существующем WebP, `download_image()` парсера считает WebP попаданием в кэш,
а `parse.yml` дополнительно убирает оригиналы с готовой WebP-парой перед
коммитом. Каскад источников фото при этом не пострадал: WebP есть у всех
позиций, а при его отсутствии сайт берёт фото с saletennis.com.

### Особенности данных (важно)

- **Артикул не уникален** (цветовые варианты одной модели) — товары идентифицируются
  по ссылке; история сравнивается **по артикулам** (как журнал парсера), т.к. сайт
  меняет slug ссылок между парсингами.
- sizes.csv может содержать товары, которых нет в products.csv — они добавляются
  автоматически с предупреждением (проверьте полноту каталога в парсере).
- «Размер» `375` нормализуется в `37,5`, «Без размера» → «—»; у струн/мячей размеры —
  это единицы продажи («сет», «бобина», «банка», «кор»).
- Текст «Нет информации о наличии» в products.csv означает, что парсер не нашёл
  таблицу наличия на странице товара — такие артикулы показываются в жёлтом
  предупреждении в шапке сайта.
- **Явный «0» в колонке магазина** products.csv = магазин возит товар, но полка пуста
  (он попадает в получатели перемещений); пустая ячейка = не возит («—»).
- **Мусорные бренды чинятся автоматически**: код поставщика «37078» → «7/6» (из
  названия), «Не определен» → бренд из названия (Diadora, Nata, …) или по фирменному
  артикулу Nike (FZ6951-110 → Nike); дубли артикулов наследуют бренд собрата.

### Ручная правка бренда (для товаров вроде шорт Nike Court Heritage)

В карточке товара (клик по названию) нажмите ✎ рядом с брендом → введите бренд →
сохраните. Правка применяется ко всем товарам с этим артикулом, хранится в браузере
и переживает перезагрузки. Чтобы зафиксировать её в данных навсегда:

1. сайдбар → **«Правки брендов: N — скачать JSON»** → получите `brand-edits.json`;
2. `npm run apply-edits -- brand-edits.json` — скрипт пропишет бренд в
   `products.csv` и `sizes.csv` по артикулу;
3. `git add public/data && git commit -m "data: правки брендов" && git push`.

**⚠️ Правка в браузере и правка в CSV живут по-разному:**

| Где правили | Переживёт следующий автопарсинг? | Видно коллегам? |
|---|---|---|
| ✎ в карточке товара | **Да**, но только в этом браузере: правка хранится в localStorage **по артикулу** и автоматически накладывается на каждую новую выборку данных (`applyBrandOverrides`). Удалится сама, когда бренд в данных станет правильным (`pruneAppliedOverrides`) | Нет |
| `npm run apply-edits` → CSV | **Нет**: бот каждый день перезаписывает `products.csv`/`sizes.csv` данными с сайта, и бренд вернётся прежним | Да, до следующего парсинга |
| Правило в парсере | **Да, навсегда**: бренд исправляется в момент сбора данных | Да |

Поэтому для «вечных» правок нужно правило в парсере, а не правка CSV.

### Бренды-линейки: `BRAND_REMAP` (Nata → 7/6)

Сайт отдаёт некоторые **линейки** как отдельный бренд. Так «Nata» — это линейка
одежды **7/6**: артикулы `NT76-4104`, `NT76-1265`, `NT76-0205`… то есть тот же
шаблон `XX76-…`, что у `TS76-BKWH`, `TB76-BL`, `KB276-BL`, а отдельного бренда
Nata в сети нет. Без правила бренд возвращался бы после каждого парсинга.

Правило продублировано в двух местах (оба обязательны):

- `parser/saletennis_parser.py` → `BRAND_REMAP` + `_normalize_brand_name()` —
  применяется и к бренду из JSON-LD страницы, и к определению по названию
  (`brand_from_name`); `parser/http_parser.py` использует те же функции;
- `src/utils/productMeta.ts` → `BRAND_REMAP` + `remapBrand()` внутри
  `cleanBrand()` — чтобы бренд был одинаковым и во встроенных данных сайта,
  и в файле, загруженном вручную.

Добавить новую линейку — одна строка в обоих файлах:

```python
BRAND_REMAP = { 'nata': '7/6', 'новая_линейка': 'НастоящийБренд' }
```

После этого достаточно одного прогона бота (или `npm run apply-edits` для
мгновенной правки текущих CSV), а локальные правки бренда в браузере очистятся
сами как избыточные.

## 💰 Скидки и 🆕 новинки

### Скидки (раздел «Распродажа» saletennis.com)

Парсер при каждом прогоне обходит публичный раздел **`/catalog/sale/`** (~20 страниц)
и пишет `public/data/discounts.json`: `itemId → {percent, price, oldPrice, name, link}`.
Из карточки товара берутся JSON-атрибут `data-ecommerce` (id, name, price, brand),
`c-item__price-old`, `c-item__price-current` и бейдж `c-item__label--sale`.

- **Цена в каталоге уже указана со скидкой** (сайт отдаёт её как основную), поэтому
  к товару добавляются только `oldPrice` и `discountPercent`;
- в «Инвентаре» — бейдж **−N%** со старой ценой (в карточках и в таблице), в карточке
  товара — зачёркнутая старая цена и бейдж «💰 Скидка N%»;
- переключатель **«💰 Со скидкой»** и сортировка **«по размеру скидки»**;
- сопоставление — по `itemId` (числовой хвост ссылки, тот же id, что в корзине),
  запасной вариант — по ссылке: slug сайт между парсингами меняет, id — нет.

Сейчас в данных **787 товаров со скидкой 25–92%**, из них 779 нашлись в каталоге.
Файл собирается заново при каждом парсинге; если раздел недоступен, парсер пишет
предупреждение и оставляет прошлый `discounts.json` (основные данные не страдают).

### Новинки (🆕)

Источник — журнал парсера `changes.csv`, события **«Новый товар»** и **«Товар
появился»** с датами (`src/utils/newProducts.ts`):

- новинка = товар, впервые появившийся в каталоге не раньше **14 дней**
  (`NEW_PRODUCT_DAYS`) от даты снимка;
- **первый парсинг журнала считается базовым срезом** и в новинки не попадает:
  на самом первом снимке «новыми» помечена половина каталога (923 товара за
  23.09.2026) — это не поступление, а старт наблюдения. Дата считается базовой,
  если на неё приходится ≥ 50% всех событий «новый товар»;
- в «Инвентаре»: бейдж **🆕 Новинка**, переключатель **«🆕 Новинки (N)»** и
  сортировка **«Сначала новинки, затем А→Я»** — она же по умолчанию, поэтому
  новые товары всегда **в самом начале списка**;
- сопоставление по артикулу (у цветовых вариантов одного артикула новинка
  подсвечивается вместе: 144 артикула = 320 позиций в каталоге).

### Сортировка «Инвентаря»

Выбор порядка запоминается в браузере (`st-inventory-sort`):

| Режим | Что делает |
|---|---|
| 🆕 Сначала новинки, затем А→Я | **по умолчанию**: новинки сверху, внутри — по названию |
| Название (А→Я) / (Я→А) | алфавитная сортировка (русская локаль) |
| Бренд, затем название | группировка по бренду |
| Остаток: больше / меньше сначала | по текущему остатку в выбранной области |
| 💰 По размеру скидки | сначала товары с максимальной скидкой |

## 🌙 Тёмная тема

Переключатель **🌙 / ☀️** в шапке справа (виден на всех вкладках и на телефоне).
Выбор запоминается в браузере (`st-theme`), при первом заходе тема берётся из
системных настроек (`prefers-color-scheme`). Класс `dark` ставится инлайн-скриптом
в `index.html` **до первой отрисовки** — белой вспышки при загрузке нет.

Технически тема — это слой переопределений цветовых утилит Tailwind
(`src/styles/dark.css`), а не сотни правок `dark:` в компонентах:

```bash
npm run build-dark    # перегенерировать src/styles/dark.css
```

Скрипт `scripts/build-dark-css.mjs` находит все цветовые классы, реально
используемые в `src/**` (сейчас 160), и строит для них тёмные эквиваленты по
HSL-правилам: пастельные фоны (…-50/100) становятся тёмными оттенками того же
тона, текст (…-600/700/800) — светлым, границы темнеют, акценты 500–700 остаются.
**Добавили новый цветовой класс в компонент — перезапустите `npm run build-dark`.**

## 🧮 Как считается аналитика

Константы — в `src/utils/analyticsCore.ts`, нормативы размеров — в `src/utils/productMeta.ts`.

### Перемещения (правила сети)

1. **Избыток в магазине → дефицит**: в Екатеринбурге/Тюмени/Уфе/Ижевске избыток —
   **больше 2 шт.** одного размера (донор оставляет 2); в Санкт-Петербурге —
   **больше 3 шт.** (оставляет 3). Получатели — магазины, где позиции **0 или 1**
   (заполняются до 2). Сначала свой город, затем межгород.
2. **Склад — без правил**: если размер есть на складе, вариант «везти со склада»
   показывается **одновременно** с магазинным — это альтернативы одного дефицита
   (выбирайте одну; приоритет складу не отдаётся).
3. **Логистика**: маршрут из СПб в другой город помечен «💸 дорого» и **скрыт по
   умолчанию** — обычно выгоднее дозаказать у поставщика.
4. **Высокий приоритет**: получатель с нулём + приоритетный размер (женские S/M,
   мужские M/L, обувь 41–44).
5. Панель «Переизбыток» показывает все позиции ≥ порога (сколько можно отдать).
6. **Профили магазинов** (`src/utils/storeRules.ts`) — последний фильтр:
   🚫 запрет товара в магазине и ⛔ ассортимент точки (вид спорта, скрытые
   категории) убирают магазин из **получателей**, 📴 выключенные перемещения —
   из **доноров и получателей**, ⭐ минимум делает точку получателем (даже при
   остатке 2 шт.) и заполняет её до `max(2, минимум)`.

|---|---|---|---|---|---|---|
| минимум | 4 | 5 | 5 | 8 | 10 | 8 |

| Мужская обувь | 41 | 42 | 42,5 | 43 | 43,5 | 44 | 44,5 | 45 | 46 | 47 |
|---|---|---|---|---|---|---|---|---|---|---|
| минимум | 8 | 11 | 11 | 11 | 11 | 10 | 8 | 6 | 3 | 1 |

Пол не определить или размер уникальный (сет/банка/ростовка/G3 и т.п.) → **минимум 4**.

**🔥 Ходовые товары** — в `public/data/hot-products.json` (редактируется без
пересборки; сейчас список пуст):

```json
{ "articles": [ { "article": "АРТИКУЛ", "minPerStore": 5, "note": "пояснение" } ] }
```

Для них действует особое правило: **минимум N штук в каждом розничном магазине**
(склад не считается). Нехватка распределяется по размерам, товар помечается 🔥-бейджем
в инвентаре, карточке и дозакупке и всегда сортируется первым.
Текущий остаток берётся по всей сети (включая склад): нехватка до норматива = заказ.

**Норматив считается только по «своим» точкам:** магазин «только падел» не должен
держать теннисный товар, поэтому профили магазинов (вид спорта, скрытые категории)
и 🚫 индивидуальные запреты товара **убирают точку из норматива** — заказ
уменьшается. 📴 Выключенные перемещения точку из норматива **не** убирают:
продавать она продолжает.

#### Состав файла заявки (XLSX)

| Артикул | Название | Бренд | Категория | Пол | Размер | Заказать, шт. |
|---|---|---|---|---|---|---|

Колонки **«В наличии (сеть)», «Норматив (сеть)», «Цена, ₽» и «Сумма, ₽» из файла
убраны** — это внутренние числа сети, поставщику они не нужны. В интерфейсе сумма
заявки осталась (карточка «Сумма заявки, ₽»): она считается внутри дашборда и в файл
не попадает. Логика — в `src/utils/supplierOrder.ts` (покрыта тестами).

Кнопка **«Заявка в XLSX»** выгружает построчную номенклатуру с учётом фильтров —
например, только бренд «7/6».

### Продажи и распроданные товары

Два источника на вкладке «🔥 Продажи»:
- **Журнал парсера (changes.csv)** — точные данные вашего парсера: «Товар закончился»,
  «Изменение количества» (старое → новое, разница), «Новый товар», «Удалён с сайта»;
- **Diff снимков** — сравнение соседних снимков истории: продажи (снижение остатка
  сети), поступления, перемещения между магазинами, распродано, attribution по
  магазинам. Первые снимки могут давать шум из-за эволюции парсера — сверяйтесь
  с журналом. Сравнение идёт **по артикулам** (сайт меняет slug ссылок между парсингами).
- **Продажи по размерам** — блок на вкладке «Продажи»: какие размеры продавались
  у мужчин/женщин/детей (популярность размерного ряда). Работает со второго снимка
  размеров: `npm run snapshot` автоматически сохраняет `sizes.csv` в
  `history/sizes-<дата>.csv` и пишет его в `manifest.json → sizeSnapshots`.
- Товары в списках продаж **кликабельны** — открывают карточку с фото и ссылкой на сайт.

## 🌐 Деплой (Vercel)

Сайт размещается на Vercel (бесплатный тариф Hobby) и защищён паролем.

### Как это работает

- Vercel сам собирает сайт: build command `npm run build`, output `dist`
  (фреймворк Vite определяется автоматически).
- Файл `middleware.ts` в корне проекта закрывает паролем **весь сайт**, включая
  CSV/JSON/фото в `/data/*`. Это бесплатный механизм Vercel Routing Middleware
  (встроенная «Password Protection» у Vercel — только на платном тарифе).
- Пароль хранится в переменной окружения `SITE_PASSWORD`
  (Settings → Environment Variables) — в коде и в git его нет.
- Посетитель вводит пароль на странице `/login`; браузер запоминает доступ
  на 30 дней (httpOnly-cookie). Выход — адрес `/logout`.
- Если `SITE_PASSWORD` не задана — сайт закрыт и показывает подсказку
  администратору (данные не утекут).
- Каждый push в главную ветку (включая ежедневные коммиты данных от
  робота-парсера) автоматически пересобирает сайт за 1–2 минуты.

### Смена пароля

Settings → Environment Variables → `SITE_PASSWORD` → Edit → новое значение →
Deployments → последний деплой → ⋯ → Redeploy.

### Деплой с нуля

1. [vercel.com](https://vercel.com) → Sign Up → войти через GitHub.
2. Add New… → Project → Import Git Repository → выбрать `TNpex/QWERTY`.
3. Перед деплоем раскрыть Environment Variables и добавить:
   ключ `SITE_PASSWORD`, значение — придуманный пароль (не от saletennis.com!).
4. Deploy. Через 1–3 минуты сайт доступен по адресу `https://<имя-проекта>.vercel.app`.

### Локальная сборка (без Vercel)

```bash
npm run build   # → dist/
```

Свой сервер: скопировать содержимое `dist/`. Внимание: защита паролем
(`middleware.ts`) работает только на Vercel.
